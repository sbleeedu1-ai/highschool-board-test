# 명세: 고등학교 공지 게시판

Status: ready-for-agent

용어는 `CONTEXT.md`를 따르고, 되돌리기 어려운 결정의 이유는 `docs/adr/0001-0003`에 있다. 2026-10-16 grill-with-docs(Q1-Q29)와 to-spec 테스트 접점 확인(Q30-Q34)에서 합의한 내용이다.

## Problem Statement

학교는 학생과 학부모에게 공지를 알릴 곳이 필요하다. 공지를 읽는 사람은 회원가입이나 로그인 없이 휴대폰이나 PC에서 최근 공지를 빨리 찾아보고 싶어 한다. 공지를 올리는 사람은 한 명(관리자)뿐이며, 공지를 쉽게 등록·수정·삭제하고 싶어 한다. 그러면서도 아무나 공지를 바꾸거나 관리자 로그인을 막아 버리지는 못해야 한다.

## Solution

누구나 볼 수 있는 웹 공지 게시판을 만든다.

- 방문자는 로그인 없이 공지 목록(최신순, 페이지 번호)과 공지 상세를 본다.
- 관리자는 숨겨진 로그인 화면으로 들어온다. 로그인하면 같은 목록·상세 화면에 [새 공지][수정][삭제] 버튼이 나타난다.
- 방문자에게는 사이트 주소 하나만 보인다. 화면과 API가 같은 주소에서 나오므로 어떤 브라우저에서도 로그인이 유지된다.
- 코드를 `main`에 병합하면 자동으로 배포되고, 배포가 실제로 끝났는지를 자동으로 확인한다.

## User Stories

### 방문자: 공지 목록

1. 방문자로서, 로그인 없이 공지 목록을 보고 싶다. 회원가입 없이 바로 공지를 확인하기 위해서다.
2. 방문자로서, 공지 목록이 최신 공지부터 보이길 원한다. 새 소식을 먼저 보기 위해서다.
3. 방문자로서, 공지가 수정되어도 목록 순서가 바뀌지 않길 원한다. 같은 공지를 같은 자리에서 다시 찾기 위해서다.
4. 방문자로서, 한 페이지에 10건씩 나뉘어 보이길 원한다. 휴대폰에서도 목록을 편하게 훑기 위해서다.
5. 방문자로서, 페이지 번호와 [이전]·[다음]으로 이동하고 싶다. 지난 공지를 찾아가기 위해서다.
6. 방문자로서, 페이지 번호가 주소에 남길 원한다. 새로고침하거나 링크를 공유해도 같은 페이지가 보이게 하기 위해서다.
7. 방문자로서, 목록에서 각 공지의 제목과 작성 날짜(`2026-10-16`)를 보고 싶다. 읽을 공지를 고르기 위해서다.
8. 방문자로서, 주소의 페이지 번호가 잘못되었으면(숫자가 아니거나 1보다 작으면) 1페이지를 보고 싶다. 깨진 화면을 보지 않기 위해서다.
9. 방문자로서, 없는 페이지 번호로 들어가면 "공지가 없습니다"와 [첫 페이지로] 버튼을 보고 싶다. 길을 잃지 않기 위해서다.
10. 방문자로서, 공지가 하나도 없을 때도 "공지가 없습니다"를 보고 싶다. 화면이 고장 났다고 오해하지 않기 위해서다.

### 방문자: 공지 상세

11. 방문자로서, 목록에서 공지를 눌러 공지 상세를 보고 싶다. 내용 전체를 읽기 위해서다.
12. 방문자로서, 본문의 줄바꿈이 그대로 보이길 원한다. 관리자가 나눈 문단대로 읽기 위해서다.
13. 방문자로서, 본문의 `http://`·`https://` 주소를 눌러 새 탭에서 열고 싶다. 안내된 링크로 바로 가기 위해서다.
14. 방문자로서, 상세에서 작성일시(`작성 2026-10-16 14:30`)를 보고 싶다. 언제 나온 공지인지 알기 위해서다.
15. 방문자로서, 수정된 공지라면 수정일시(`· 수정 2026-10-17 09:00`)도 보고 싶다. 내용이 바뀌었음을 알기 위해서다.
16. 방문자로서, 모든 날짜를 한국 시간으로 보고 싶다. 시차 때문에 헷갈리지 않기 위해서다.
17. 방문자로서, 공지 상세 주소를 공유하고 싶다. 다른 사람에게 특정 공지를 바로 보여 주기 위해서다.
18. 방문자로서, 삭제되었거나 없는 공지 주소로 들어가면 "공지를 찾을 수 없습니다"와 [목록으로] 버튼을 보고 싶다. 목록으로 돌아가기 위해서다.
19. 방문자로서, 상세에서 목록으로 돌아갈 때 보던 페이지로 가고 싶다. 다시 찾지 않기 위해서다.
20. 방문자로서, 본문에 악성 코드가 섞여 있어도 실행되지 않길 원한다. 안전하게 읽기 위해서다.

### 방문자: 공통

21. 방문자로서, 화면이 모두 한국어이길 원한다.
22. 방문자로서, 휴대폰에서도 화면이 잘 보이길 원한다. 대부분 휴대폰으로 확인하기 때문이다.
23. 방문자로서, 서버나 네트워크 문제가 생기면 "잠시 후 다시 시도해 주세요"와 [다시 시도] 버튼을 보고 싶다. 무엇을 해야 할지 알기 위해서다.
24. 방문자로서, 관리자 로그인 링크나 관리 버튼을 보고 싶지 않다. 화면이 단순하기를 원하기 때문이다.

### 관리자: 로그인과 로그인 유지

25. 관리자로서, 관리자 로그인 주소로 들어가 아이디와 비밀번호로 로그인하고 싶다. 공지를 관리하기 위해서다.
26. 관리자로서, 로그인에 실패하면 "아이디 또는 비밀번호가 올바르지 않습니다"만 보고 싶다. 어느 쪽이 틀렸는지 공격자에게 알려 주지 않기 위해서다.
27. 관리자로서, 로그인한 뒤 30분 동안 활동하지 않으면 자동으로 로그아웃되길 원한다. 학교 공용 PC에서 로그인한 채로 두는 위험을 줄이기 위해서다.
28. 관리자로서, 활동하는 동안에는 로그인이 계속 유지되길 원한다. 작성 중에 갑자기 쫓겨나지 않기 위해서다.
29. 관리자로서, Safari와 아이폰에서도 로그인이 유지되길 원한다. 어떤 기기에서든 관리하기 위해서다.
30. 관리자로서, 직접 로그아웃하고 싶다. 공용 PC에서 일을 마칠 때 쓰기 위해서다.
31. 관리자로서, 로그아웃 버튼은 로그인한 상태에서만 보이길 원한다.
32. 관리자로서, 서버가 재배포되면 다시 로그인해야 한다는 점을 받아들인다. 대신 구조를 단순하게 유지한다.
33. 관리자로서, 비밀번호를 바꾸고 싶을 때 로컬 명령으로 새 해시를 만들고 배포 설정만 바꾸고 싶다. 비밀번호 원문이 어디에도 남지 않게 하기 위해서다.

### 관리자: 로그인 잠금

34. 관리자로서, 같은 접속 위치에서 5번 연속 로그인에 실패하면 그 위치가 10분 동안 로그인 잠금되길 원한다. 비밀번호 대입 공격을 늦추기 위해서다.
35. 관리자로서, 다른 위치에서 누가 틀린 비밀번호를 넣어도 내 로그인은 막히지 않길 원한다. 공격자가 나를 잠가 버리지 못하게 하기 위해서다.
36. 관리자로서, 로그인 잠금 중에는 "잠시 후 다시 시도해 주세요"를 보고 싶다.
37. 관리자로서, 10분이 지나면 다시 로그인을 시도할 수 있길 원한다.
38. 관리자로서, 로그인에 성공하면 그 위치의 실패 횟수가 초기화되길 원한다.

### 관리자: 공지 등록

39. 관리자로서, 공지 목록에서 [새 공지]를 눌러 등록 화면으로 가고 싶다.
40. 관리자로서, 제목과 본문을 입력해 공지를 등록하고 싶다.
41. 관리자로서, 입력하는 동안 글자 수(예: `37/100`)를 보고 싶다. 제한을 넘기 전에 알기 위해서다.
42. 관리자로서, 제목이 비었거나 100자를 넘으면 그 칸 아래에서 안내를 보고 싶다.
43. 관리자로서, 본문이 비었거나 5,000자를 넘으면 그 칸 아래에서 안내를 보고 싶다.
44. 관리자로서, 공백만 입력한 제목·본문은 거부되길 원한다. 빈 공지가 올라가지 않게 하기 위해서다.
45. 관리자로서, 앞뒤 공백은 자동으로 지워지길 원한다.
46. 관리자로서, 등록하면 새 공지 상세로 이동하고 싶다. 결과를 바로 확인하기 위해서다.
47. 관리자로서, 로그인하지 않은 상태로 등록 주소에 들어가면 로그인 화면으로 가길 원한다.

### 관리자: 공지 수정

48. 관리자로서, 공지 상세에서 [수정]을 눌러 기존 내용이 채워진 수정 화면으로 가고 싶다.
49. 관리자로서, 수정할 때도 등록과 같은 입력 제한과 안내를 받고 싶다.
50. 관리자로서, 수정을 저장하면 공지 상세로 돌아가 수정일시가 표시되길 원한다.
51. 관리자로서, 창 두 개에서 같은 공지를 고치면 나중에 저장한 내용이 남는다는 점을 받아들인다.
52. 관리자로서, 이미 삭제된 공지를 수정하려 하면 "공지를 찾을 수 없습니다"를 보고 싶다.
53. 관리자로서, 작성 중에 로그인이 만료되면 로그인 화면으로 이동하되, 작성 중인 내용을 잃을 수 있다는 안내를 보고 싶다.

### 관리자: 공지 삭제

54. 관리자로서, 공지 상세에서 [삭제]를 누르면 "정말 삭제할까요?" 확인 창을 보고 싶다. 실수로 지우지 않기 위해서다.
55. 관리자로서, 확인하면 공지가 완전히 삭제되고 공지 목록으로 돌아가길 원한다.
56. 관리자로서, 삭제가 되돌릴 수 없다는 점을 받아들인다(휴지통 없음).
57. 관리자로서, 이미 삭제된 공지를 삭제하려 하면 "공지를 찾을 수 없습니다"를 보고 싶다.

### 관리자: 보안 오류

58. 관리자로서, 보안 토큰 문제로 요청이 거절되면 "다시 시도해 주세요"를 보고 싶다.
59. 관리자로서, 다른 사이트가 내 로그인을 몰래 이용해 공지를 바꾸지 못하길 원한다.

### 운영과 보안

60. 운영자로서, 백엔드 주소로 직접 들어오는 요청은 거절되길 원한다. 로그인 잠금을 우회하지 못하게 하기 위해서다.
61. 운영자로서, 배포 플랫폼의 상태 확인만은 직접 접근을 허용하길 원한다. 배포 성공을 판정하기 위해서다.
62. 운영자로서, 관리자 계정·비밀값·DB 접속 정보가 저장소에 들어가지 않길 원한다. 공개 저장소이기 때문이다.
63. 운영자로서, 방문자 화면 요청이 무료 한도에 포함되지 않길 원한다. API 요청만 하루 10만 건 한도에 들어간다.

### 개발자: 로컬 개발

64. 개발자로서, 백엔드와 프론트를 각각 명령 하나로 로컬에서 실행하고 싶다.
65. 개발자로서, 로컬에서도 운영처럼 주소 하나로 화면과 API를 쓰고 싶다. 운영과 다르게 동작하는 문제를 줄이기 위해서다.
66. 개발자로서, 로컬에서는 HTTPS와 비밀 헤더 없이도 로그인할 수 있길 원한다.
67. 개발자로서, 로컬 DB 데이터가 재시작 후에도 남길 원한다.
68. 개발자로서, 로컬 관리자 계정을 git에 올라가지 않는 파일에 두고 싶다.

### 개발자: DB와 CI/CD

69. 개발자로서, 표 구조를 버전별 마이그레이션으로만 바꾸고 싶다. 로컬·테스트·운영 DB 구조를 똑같이 유지하기 위해서다.
70. 개발자로서, 코드와 실제 표 구조가 다르면 서버가 기동 단계에서 실패하길 원한다.
71. 개발자로서, PR마다 백엔드 테스트, 프론트 검사·테스트·빌드가 자동으로 돌길 원한다.
72. 개발자로서, CI가 실제 PostgreSQL로 마이그레이션과 서버 기동을 확인하길 원한다. H2에서만 통과하는 SQL을 운영 전에 잡기 위해서다.
73. 개발자로서, `main`에 병합되면 CI 통과 후에만 백엔드와 프론트가 자동 배포되길 원한다.
74. 개발자로서, 프론트만 바뀌면 백엔드는 재배포되지 않길 원한다.
75. 개발자로서, 배포 뒤 운영 API가 이번 커밋으로 응답하는지 자동으로 확인받고 싶다. "배포 완료"를 추측하지 않기 위해서다.
76. 개발자로서, 첫 배포 직후 운영 사이트에서 전체 흐름을 브라우저 자동 테스트로 한 번 확인하고 싶다.
77. 개발자로서, 브라우저 자동 테스트가 만든 테스트 공지가 끝에 반드시 지워지길 원한다. 방문자가 보지 않게 하기 위해서다.

## Implementation Decisions

### 구조

- 한 저장소에 두 모듈을 둔다.
  - **백엔드**: JSON API만 제공한다. Spring Boot 4.1.1, Kotlin(Spring Boot가 관리하는 버전), Java 21, Gradle Kotlin DSL, Spring Data JPA, Spring Security, Flyway, Actuator.
  - **프론트**: 화면 전체와 Pages Functions(API 전달 코드)를 둔다. Vite + React + TypeScript, shadcn/ui(Tailwind v4), Node 24 LTS, npm.
  - 두 모듈을 묶는 루트 빌드 도구는 두지 않는다.
- 방문자에게 보이는 주소는 Cloudflare Pages 하나다. Pages Functions가 `/api/*`를 Railway 백엔드로 전달한다(ADR-0001). CORS 설정은 두지 않는다.
- 로컬에서는 Vite 개발 서버가 `/api/*`를 로컬 백엔드로 프록시한다.

### 공지 모델과 스키마

- 공지 표: 식별자, 제목, 본문, 작성일시, 수정일시. 시각은 UTC로 저장한다.
- 수정일시는 수정한 적이 없으면 비워 둔다. "수정된 공지"는 수정일시가 있는 공지다.
- 공지 목록 정렬: 작성일시 내림차순, 같으면 식별자 내림차순.
- 표 구조 변경은 Flyway 마이그레이션으로만 한다. JPA는 검사(`validate`)만 한다.

| 메서드·경로 | 권한 | 설명 |
|---|---|---|
| `GET /api/notices?page=N` | 모두 | 공지 목록. 10건, 페이지 정보(현재 페이지, 전체 페이지 수, 전체 건수) 포함 |
| `GET /api/notices/{id}` | 모두 | 공지 상세 |
| `POST /api/notices` | 관리자 | 공지 등록. 생성된 공지 반환 |
| `PUT /api/notices/{id}` | 관리자 | 공지 수정 |
| `DELETE /api/notices/{id}` | 관리자 | 공지 완전 삭제 |
| `POST /api/auth/login` | 모두 | 로그인. 세션 쿠키 발급 |
| `POST /api/auth/logout` | 관리자 | 로그아웃 |
| `GET /api/auth/me` | 모두 | 로그인 상태 확인(화면이 버튼 표시 여부를 정함) |
| `GET /api/version` | 모두 | 배포된 커밋 번호(배포 완료 확인용) |
| Actuator 상태 확인 | 직접 접근 허용 | Railway 헬스체크 |

- 페이지 번호는 1부터 센다. 숫자가 아니거나 1보다 작으면 1로 본다. 범위를 넘으면 빈 목록을 돌려준다.
- 입력 검사(백엔드가 최종 판정): 제목은 앞뒤 공백을 지운 뒤 1-100자, 본문은 앞뒤 공백을 지운 뒤 1-5,000자.
- 오류 응답 형식: `code`, `message`, `fieldErrors`(칸 이름과 안내 목록).

| 상황 | 상태 코드 |
|---|---|
| 입력 오류 | 400 |
| 로그인 안 됨 / 세션 만료 | 401 |
| CSRF 토큰 오류, 비밀 헤더 없음·틀림 | 403 |
| 없는 공지 | 404 |
| 로그인 잠금 | 429 |
| 그 밖의 서버 오류 | 500 |

### 인증과 보안

- 관리자 계정은 DB에 두지 않는다. 아이디와 비밀번호 해시를 환경변수로 받는다(ADR-0002). 해시는 로컬 전용 Gradle 명령으로 만든다. 이 명령은 비밀번호를 입력받아 해시만 출력하고 원문은 저장하지 않는다.
- 로그인 유지: 서버 메모리 세션. 쿠키는 HttpOnly·Secure, 30분 무활동 시 만료. "로그인 유지" 기능은 없다. Railway 인스턴스는 1대로 고정한다.
- CSRF는 Spring Security의 SPA 설정(`csrf.spa()`)으로 막는다.
- 프록시 비밀 헤더(ADR-0003): Pages Functions가 `X-Client-IP`(방문자 IP)와 `X-Proxy-Secret`을 붙인다. 백엔드는 비밀값이 맞을 때만 그 IP를 믿는다. 비밀값이 없거나 틀린 요청은 상태 확인을 빼고 모두 거절한다.
- 로그인 잠금: 접속 위치(IP)별로 5회 연속 실패하면 10분 동안 막는다. 성공하면 횟수를 초기화한다. 기록은 메모리에만 둔다.
- 현재 시각은 교체할 수 있는 **시계** 하나에서 읽는다. 로그인 잠금 만료, 작성일시, 수정일시가 모두 이 시계를 쓴다.
- `local` 프로필에서는 Secure 쿠키와 비밀 헤더 검사를 끈다.

### Pages Functions(API 전달)

- 핵심 로직은 **"들어온 요청 + 설정값 → 백엔드로 보낼 요청"을 만드는 순수 함수** 하나로 분리한다. 이 함수가 하는 일은 세 가지다.
  - 경로와 쿼리, 메서드, 본문, 쿠키, CSRF 헤더를 그대로 옮긴다.
  - 방문자 IP를 `X-Client-IP`로 붙인다.
  - `X-Proxy-Secret`을 붙인다.
- 백엔드 주소와 비밀값은 Pages 환경변수로 받는다.
- 백엔드 응답(상태 코드, 쿠키 포함)은 그대로 돌려준다.

### 화면

| 화면 주소 | 내용 |
|---|---|
| `/` (`?page=N`) | 공지 목록. 관리자 로그인 시 [새 공지] |
| `/notices/:id` | 공지 상세. 관리자 로그인 시 [수정][삭제] |
| `/admin/login` | 로그인. 방문자 화면에는 링크를 두지 않는다 |
| `/admin/notices/new` | 공지 등록 |
| `/admin/notices/:id/edit` | 공지 수정 |

- 로그인하지 않고 관리자 화면에 들어오면 로그인 화면으로 보낸다. 로그아웃 버튼은 로그인 상태에서만 보인다.
- 본문은 일반 텍스트로 보여 준다. 줄바꿈은 살리고, `http(s)://` 주소만 새 탭 링크(`noopener`)로 바꾼다. HTML을 그대로 넣는 방식은 쓰지 않는다.
- 날짜는 한국 시간으로 표시한다. 목록은 `YYYY-MM-DD`, 상세는 `작성 YYYY-MM-DD HH:mm`이고, 수정된 공지만 `· 수정 YYYY-MM-DD HH:mm`을 덧붙인다.
- 화면별 오류 처리는 User Stories 18, 23, 42-43, 52-53, 58을 따른다.

### 환경별 DB

| 프로필 | DB |
|---|---|
| `local` | H2 파일(git 제외) |
| `test` | H2 메모리 |
| `prod` | Railway PostgreSQL. `PGHOST`·`PGPORT`·`PGUSER`·`PGPASSWORD`·`PGDATABASE`를 참조 |

H2는 PostgreSQL 호환 모드로 띄운다.

### CI/CD

- **CI**(PR과 `main` push): 백엔드 테스트, PostgreSQL 서비스 컨테이너로 마이그레이션·기동 확인, 프론트 lint·타입 검사·Vitest·빌드.
- **백엔드 배포**: Railway GitHub 자동배포.
  - Root Directory는 백엔드 폴더, Watch Paths도 백엔드 폴더로 지정한다.
  - "Wait for CI"를 켠다.
  - 헬스체크는 Actuator 상태 확인 경로를 쓴다.
- **프론트 배포**: `main`에서 CI가 통과하면 GitHub Actions가 빌드한 뒤 `cloudflare/wrangler-action@v4`의 `pages deploy`로 배포한다. GitHub 시크릿은 `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`다.
- **비밀값(값은 어디에도 적지 않는다)**
  - Railway: 관리자 아이디, 관리자 비밀번호 해시, 프록시 비밀값, `SPRING_PROFILES_ACTIVE=prod`, Postgres 참조
  - Pages: 백엔드 주소, 프록시 비밀값
- **배포 완료 기준**(모두 만족)
  - (a) Railway 헬스체크 200, 새 배포 활성
  - (b) Pages 배포 성공
  - (c) Actions가 Pages 주소의 `/api/version` 커밋 번호(`RAILWAY_GIT_COMMIT_SHA`)가 이번 push 커밋과 같아질 때까지 최대 10분 확인한 뒤, `/api/notices`가 200
- PR 미리보기 배포는 하지 않는다.

## Testing Decisions

### 좋은 테스트의 기준

- 바깥에서 보이는 동작만 확인한다: API 응답(상태 코드, 본문, 쿠키), 순수 함수의 입력과 출력, 화면 흐름.
- 내부 부품(서비스·저장소 계층, 화면 부품)의 구현을 따로 테스트하지 않는다. 구현을 바꿔도 동작이 같으면 테스트가 깨지지 않아야 한다.
- 경계값은 양쪽을 모두 확인한다(통과하는 마지막 값과 거부되는 첫 값).

### 테스트 접점(5개)

1. **백엔드 HTTP API (주 접점)**: Spring 통합 테스트로 API를 바깥에서 호출한다. 보안 필터, 입력 검사, H2 메모리 DB를 모두 거친다. 비밀 헤더와 방문자 IP는 테스트가 요청에 직접 붙여 Pages Functions를 흉내 낸다. 확인할 것:
   - 공지 목록·상세·등록·수정·삭제
   - 미로그인 401, CSRF 없음 403, 비밀 헤더 없음·틀림 403(상태 확인은 허용), 없는 공지 404
   - 경계값: 제목 100/101자, 본문 5,000/5,001자, 공백만 입력
   - 페이지 규칙: 잘못된 번호는 1로, 범위 초과는 빈 목록, 정렬, 수정해도 순서 불변
   - 로그인·로그아웃, 세션 쿠키 속성
   - 로그인 잠금: 같은 IP에서 5회 실패 후 429, 다른 IP는 영향 없음, 시계를 10분 앞으로 돌리면 해제, 성공 시 초기화
2. **시계**: 교체할 수 있는 시계로 로그인 잠금 만료와 작성일시·수정일시를 결정적으로(매번 같은 결과로) 확인한다. 1번 접점 안에서 쓴다.
3. **프론트 순수 함수 (Vitest)**
   - 페이지 번호 해석
   - 링크 자동 변환: http(s)만 바꾸고, `<script>`·`javascript:` 주소는 실행 가능한 형태가 되지 않는지
   - 날짜 형식: UTC를 한국 시간으로 바꾸고, 수정 표시 여부
4. **Pages Functions 요청 변환 함수 (Vitest)**: `X-Client-IP`와 `X-Proxy-Secret`이 붙는지, 경로·쿼리·메서드·본문·쿠키가 보존되는지, 방문자가 보낸 가짜 `X-Proxy-Secret`·`X-Client-IP`를 덮어쓰는지.
5. **시스템**
   - CI에서 실제 PostgreSQL로 Flyway 마이그레이션과 서버 기동을 확인한다.
   - Playwright로 첫 배포 직후 운영 주소를 1회 테스트한다(CI 상시 실행 아님). 흐름은 목록·상세 → 로그인 → 등록·수정·삭제 → 로그아웃이다. 테스트 공지 제목은 `[E2E 테스트]`로 시작하고 끝에 반드시 삭제한다.
   - **로그인 잠금은 E2E에 넣지 않는다.** 운영에서 테스트하는 IP가 잠기기 때문이다.
   - 그다음 사람이 점검표로 확인한다.

### 참고할 기존 테스트

없다. 저장소에 코드가 아직 없다. 첫 티켓에서 만드는 테스트가 이후 테스트의 본보기가 된다.

### 구현 완료 기준

CI 통과 + 배포 완료 기준 (a)(b)(c) + E2E 1회 통과 + 사람 점검표 확인.

## Further Notes

### 작업 방식

기능 브랜치 → PR → 사용자 확인 후 `main` 병합. 병합한 브랜치는 삭제한다(`docs/agents/handoff.md`).

### 공식 문서로 확인한 사실 (2026-10-16)

- Spring Boot 최신 안정은 4.1.1(2026-08-20)이고 4.2.0은 마일스톤이다. Java 17-26 지원, Gradle 8.14+/9.x. Kotlin은 2.2 이상이며 버전은 Boot가 관리한다. kotlin-spring 플러그인과 `-Xannotation-default-target=param-property`를 권장한다.
- Railpack은 루트 디렉터리에 Gradle wrapper가 있으면 Java로 인식한다. JDK 기본값은 21(`RAILPACK_JDK_VERSION`으로 변경).
- Railway
  - 모노레포는 Root Directory로 지정하고, 설정 파일은 절대경로로 지정한다.
  - 헬스체크는 2xx 응답이 와야 새 배포를 활성화하며, 기본 대기 시간은 300초다. 앱은 `PORT` 환경변수로 listen한다.
  - "Wait for CI"는 push 트리거 워크플로가 있어야 켤 수 있고, 실패하면 배포가 SKIPPED된다. 커뮤니티에는 Redeploy 시 이 설정이 꺼진다는 보고가 있다.
- Cloudflare
  - `pages-action`은 보관(archived)되었으므로 `wrangler-action@v4`를 쓴다.
  - Functions 폴더는 Pages 프로젝트 루트에 둔다(빌드 결과 폴더 밖).
  - 무료 플랜에서 Functions 요청은 하루 10만 건 한도에 포함되고, 정적 파일 요청은 무제한이다.
  - 최상위 `404.html`이 없으면 SPA로 처리한다.
  - Worker가 외부로 보내는 요청에는 방문자 IP가 자동으로 전달되지 않는다.
- Vite 8.3.x는 Node 20.19+/22.12+가 필요하다. shadcn/ui는 Tailwind v4와 `@/*` 경로 별칭을 쓴다.
- Spring Security 7.1은 SPA용 `csrf.spa()`를 공식 권장한다.
